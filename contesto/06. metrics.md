# Metrics: what the system has to be able to say about itself

_Written on 2026-09-26, before any code. It says what is measured and why, where each figure's truth
lives, and what is stored. The subsystem is `metrics` (`webtools_metrics`)._

References: `contesto/02. current_context.md` (the flow, the price model),
`contesto/04. worst_case_cost_analysis.md` (the estimates these measurements replace with figures),
`CLAUDE.md` (the general rules every subsystem obeys).

---

## 1. What this is, and what it is not

**It is not a log.** A log keeps one line per occurrence and is read by a person when something has
gone wrong. Logging is a separate job, to be done separately. Here nothing is kept per occurrence:
a turn of chat does not become a document, a request does not become a row. What arrives is folded
into a number that was already there, and what is stored is the number.

**It is metrics, technical and commercial.** Technical: how long things take, how often a provider
fails, how many tokens a phase burns, which routes answer with which status. Commercial: how many
requests arrive, how many survive each gate, how many demos are accepted, and how much a webtool
really consumes. Both across **the whole system** — every subsystem measures, not
only the preanalyst.

**It covers the whole pipeline, not only what exists today.** The names of the later gates are in
the vocabulary from the start: the day the demo exists, nobody has to remember to add it.

## 2. Two readers, and what follows from the difference

**We read it to know whether the thing stands up.** Three figures are the ones we do not have: the
real AI cost of a webtool, how often demos are accepted, how many turns a pre-analysis really
takes. Every figure in `03.`, `04.` and `05.` is an estimate with its assumptions written beside it,
and none has been checked against a real project.

**The pipeline reads what a project consumed in order to work out a price.** In the consumption
tier the price is `the project's real cost of consumption + the driver's share`, said at the demo
and refusable. In autonomous work the system takes the consumed tokens off the driver's credit at
every step.

They do not need the same thing. A lost measurement is a slightly wrong average for the first
reader and a wrong invoice for the second. **Therefore the money at the demo is not taken from
here**: what a project consumed is written on its own pipeline steps in anagraphics, in the same
awaited write that records the step. Metrics keeps its own per-project total as well (§4), in
tokens, and the two can be compared — but when they disagree, the project's record is the one that
is right. **And here it is only ever tokens**: converting one into money is a rate, the rate is
agreed elsewhere and changes, and a figure in a currency coming out of this subsystem would be a
claim about a price nobody configured in it.

## 3. Where each figure's truth lives

Three sources, and each figure takes the one it belongs to. This is the part the first draft of this
document got wrong, by wanting everything pushed.

**a. What is already written down, and is true by construction: anagraphics.** The projects, their
pipeline steps with `result`, `state` and `decided_at`, the drivers, the discounts, the users'
credit. The commercial funnel — how many projects, at which gate, with which outcome, whose driver,
which discount — is a **read** of that, not a count of messages somebody remembered to send. Metrics
is generally passive, but this is a case where it acts: it asks anagraphics and computes.

**b. What leaves no trace anywhere: pushed measurements.** Everything that never becomes a project
or a step, and everything that has no state at all:

- the form opened, filled in part, abandoned; the login asked for and not completed;
- **how long anything takes**. The observation that started this — an opening of 15 s and an
  ordinary turn of 137 s against a `timeout_ms` of 120 000, so a retry inside the SDK — exists only
  as a sentence in a checkpoint;
- a provider that **fails**, as against one that refuses: in the log a `503` and a service that is
  down look alike;
- what an attempt consumed that never became a step, because the call threw before anything was
  written;
- the HTTP surface of every subsystem: requests by route and status, and their duration.

**c. What has to be declared, not discovered: which kinds of token a provider counts.** That list
is configuration, per provider, and it is what a measurement's tokens are checked against (§5).

## 4. What is stored: two collections, and nothing per occurrence

**`metrics_daily` — one document per day × metric × dimensions.** A measurement that arrives is an
`$inc` on the document that is already there, created by upsert the first time. One turn of chat
does not add a document; it adds 1 to a counter, its tokens to four sums, and 1 to the bucket its
duration falls in:

    { "day": "2026-09-26", "subsystem": "preanalyst", "metric": "preanalysis.turn",
      "dims": { "model": "claude-opus-5", "outcome": "passed" },
      "count": 412,
      "tokens": { "input": 754321, "output": 251004, "cached_read": 10934221, "cached_write": 0 },
      "duration_ms": { "sum": 56489204, "min": 8912, "max": 210400,
                       "buckets": { "5000": 3, "15000": 41, "60000": 190, "120000": 150,
                                    "300000": 28, "inf": 0 } } }

The number of documents depends on how many **kinds** of thing are measured, not on how much
traffic there is: about thirty metric-and-dimension combinations across the five subsystems make
~30 documents a day, ~11 000 a year, a handful of megabytes. Ten clients or ten thousand make the
same number of documents.

**`metrics_projects` — one document per project.** A per-project total cannot come out of daily
buckets: "what a webtool consumes" is a distribution **over projects**, and a daily sum has already
thrown the projects away. One accumulator per project, updated by `$inc` exactly like the buckets:
tokens by phase, turns used, seconds waited, the gates it passed. A thousand projects are a
thousand documents, and they give the median and the tail, not just the mean.

**Nothing else is stored.** No document per turn, per call or per request.

**Percentiles come from the buckets**, whose edges are configured (`limits.duration_buckets_ms`).
`p50` and `p95` read off a histogram are estimates, bounded by the bucket that contains them, and
the answers say so. Keeping every duration to get an exact percentile is the log we are not
building. `min` and `max` are exact, because they cost one field each.

## 5. The providers, and why nothing is priced

Configuration says, per provider, which kinds of token that provider reports:
`providers.<provider>.token_kinds`. A list of names, and nothing else. It is what a measurement's
tokens are checked against — tokens for a provider nobody declared, or of a kind that provider does
not count, are refused by name — and it exists so that no list of kinds has to live in the code, at
any level. One provider counts input and output, another a cache it writes and a cache it reads,
another reasoning apart.

**There is no price table.** What a token is worth is not this subsystem's to say: a price belongs
to a provider **and** a model, it is agreed rather than measured, and it changes. What is kept here
is the count, by kind — which is what a price would have been worked out from anyway, and keeping it
unconverted means the question can be answered later, deliberately, from numbers that were never
rounded into a figure nobody checked.

For the same reason **the kinds are never added to one another**. The session of 2026-09-19 is why:
26.5 M tokens read from cache against 282 tokens of fresh input were worth about a seventh of what
the same count of fresh input would have been. A single number over the four would be a rate between
them, which is a price by another name. Every figure that could be one is given kind by kind.

## 6. The vocabulary

Metric names are a **closed list**, like `PipelineStepName` in anagraphics: a name not in the list
is a `400`, not a new kind of number nobody will ever query. A typo must not become a counter that
is never read and never missed. The list grows by decision; what follows is what it is worth
measuring from the first day, and it is deliberately wider than the three questions of §2,
because a metric that starts being collected in December cannot answer a question about October.

Every metric carries, when it applies: `count`, `duration_ms`, `tokens`, `bytes`. Dimensions are
listed per metric.

### a. Every subsystem, from the shared client

| metric | dimensions | what it answers |
|---|---|---|
| `http.request` | subsystem, route, method, status | load, errors and duration of every surface we expose |
| `http.error` | subsystem, code | which stable error codes actually happen, and how often |
| `http.refused_ip` | subsystem | requests turned away by the allowlist: a misconfiguration, or somebody knocking |
| `dependency.call` | subsystem, target, operation, outcome | **one subsystem calling another**: the preanalyst asking anagraphics for a user, the sso exchanging a ticket. Duration and failures. When a page is slow this is the metric that says whose fault it is |
| `mongo.operation` | subsystem, collection, operation, outcome | the database's own latency and failures, where somebody talks to it directly |
| `process.started` | subsystem, outcome (ok, configuration_missing) | restarts, and starts that never happened because a configuration field was missing. A count that grows by itself is a process that is crashing |

### b. The AI: what it consumes, how long it takes, how often it misbehaves

| metric | dimensions | what it answers |
|---|---|---|
| `ai.call` | subsystem, phase, model, provider, outcome (ok, timed_out, refused, unusable) | calls, tokens by kind, duration. The four outcomes are told apart because they mean different things and only one of them consumes nothing |
| `ai.failed` | subsystem, phase, provider, reason | a provider that is **down** as against one that **refuses**: today both end as `503 PREANALYST_UNAVAILABLE` in a log that gets rotated. It carries the tokens spent anyway, because in a failed attempt the model may well have run |
| `ai.retry` | subsystem, phase, provider | retries inside the SDK. The 137 s turn against a 120 s timeout was one of these, and nothing counted it |
| `preanalysis.validation` | outcome (accepted, sent_back) | how often the validator sends the preanalyst back. It is the quality of the preanalyst measured by a second engine, and every `sent_back` is one more call |

### c. The funnel and the pipeline's timing

Mostly **read from anagraphics** (§3a), because the projects and their steps are the truth; the
first two are pushed, because they leave no trace.

`prespec.truncated` used to be here, counting the pre-specifications cut at the character limit. It
was removed on 2026-09-28 with the thing it measured: the two cuts were defects, not a limit anybody
had decided, and an over-long answer now makes the submission fail with a message instead of being
shortened in silence. A metric of a defect goes when the defect goes — left behind, it would be a
name in a closed vocabulary that nothing can ever send.

| metric | dimensions | what it answers |
|---|---|---|
| `form.opened` | — | how many people reach the form |
| `form.submitted` | outcome (sent, abandoned, login_required) | how many finish it, after how long, and where the others stop |
| `project.created` | autonomous_work, has_discount, has_ambassador | the entries, and how they arrived |
| `gate.decided` | gate, outcome, reason | every gate: prevalidation, pre-analysis, driver and client validation, demo, payment. `reason` carries the refusal's own name (`non_sequitur`, `run_out_certain`, …), which is what says **why** we lose people |
| `gate.duration` | gate | **how long a project sits at each gate**, from opening to decision. It is a cost — the driver's hours are counted on every project in the funnel, not only on the ones that sell — and it is the lead time the client feels |
| `project.lead_time` | outcome | from `project.created` to the last gate: how long a project takes end to end |
| `preanalysis.turn` | provider, model, outcome | the turns: tokens, duration |
| `preanalysis.closed` | outcome (ready, turns_exhausted, abandoned) | how many pre-analyses arrive at an end, and how |
| `underspecified.returned` | attempt | how many times a request goes back for more detail, and at which attempt. Each round is a full prevalidation run again |

### d. Turns and tokens

| metric | dimensions | what it answers |
|---|---|---|
| `turns.granted` | source (purchase, fake_purchase, included) | turns put into a user's credit, and where they came from |
| `turns.spent` | phase | turns actually consumed. Against `turns.granted` it says whether the included allowance is right |
| `tokens.charged` | driver_uid, provider, model | autonomous work: the tokens taken off a driver's credit |

### e. What is computed on reading, and stored nowhere

These need no new counter: they are the questions the ones above were chosen to answer.

- **Conversion, gate by gate**, and end to end. `04.` assumes 20%; this says what it is.
- **Tokens per accepted demo** — every token of the period divided by the demos accepted in it,
  kind by kind, which is the real unit consumption of a sale, the one the worst case builds five
  pipelines out of.
- **What we refuse consumed**: the tokens of projects whose last gate was a refusal, by reason. It
  is the part of the consumption that produces nothing, and nobody is measuring it anywhere today.
- **The cache ratio** per phase: `cached_read` against `input`. On 2026-09-19 that ratio was the
  difference between $19 and $137, and it is the cheapest lever we have.
- **Failure rate** per provider and phase: `ai.failed` over `ai.call`, and the same for
  `dependency.call`.
- **p50 and p95** of every duration, from the buckets, with the bucket's own width as the error.

### f. What was added on 2026-09-29, after reading the whole code back

The tables above were written before any code. A pass over everything that was built afterwards
found facts the code already had in hand and no metric named, names the vocabulary declared and
nothing sent, and one figure that was wrong rather than missing. What was decided, and why — the
detail is in `docs/subsystems/metrics/README.md` §4, which is the reference.

**One figure was wrong.** `gate.duration` named the interval after the step that **closed** it, and
under the pipeline's convention a step that is `open` is closed by whatever comes next — which may
belong to another gate. The rounds of questions are opened by the preanalyst and closed by the
analyst's own opening step, so the whole conversation was filed under `analysis`, added in the same
bucket to the run's own minutes; and `preanalysis` recorded the few hundred milliseconds between two
HTTP calls. The longest wait in the pipeline, the one the client actually feels, had no bucket of
its own. It is now named after the gate that **was** open, and nothing is reported when nothing was:
the interval between one gate deciding and the next writing anything is dead time, which is real and
is a different question.

**Facts the code had and nothing named.**

| what | where it was already known | why it is worth a number |
|---|---|---|
| `fell_back` on `ai.call` | a required field of all six door contracts, written on every step | a configured model that was changed and a primary model being fallen back from every time are the same bucket without it, and they cost different money |
| `ai.unusable` | every door turns a `complete` answer into an unusable one and says why | `ai.call` is sent when the call comes back, before anybody has read the answer: the door's own verdict was recorded nowhere, so "answers in schema and says nothing" — the likely failure — had no figure at all |
| `driver_link.resolved` | nine states in `driver_link.js`, four more for the ambassador | five of the driver states and three of the ambassador's are money somebody was owed and will not be paid, and the project is written `driver_uid: null` either way, so it cannot be recovered afterwards |
| `configuration.changed` | `PUT /configuration/{subsystem}/pricing` | the moment after which every cost figure means something else |
| `measurement.refused` | metrics answers `400` and the sender counts it privately | the one failure the closed list exists in order to create was the only one nobody could see |
| `reason` on `gate.decided` from the analyst | the step already says `failed_at` | a run that dies on a defect of ours read the same as a provider that timed out |
| `reason` on `form.submitted` | `readAnswers` already says which fields were empty or too long | five refusals under one word read as "the form does not work" |
| `reason` on `login.attempt` | the four refusals are told apart internally already | told to nobody, on purpose; counted, because a password nobody set is not a password typed wrong |
| `amounts.registered` on `driver.chosen` | the list was already read | one enabled out of one needs drivers; one out of twenty needs interviews |

**Names that were declared and nothing sent.** `http.error` and `dependency.call` from the sso;
`dependency.call` towards the **sso**, which sits on the path of every page of every subsystem and
was the one leg the metric could not see; every measurement from `configurator-fe`, which had the
client configured and deployed and never loaded it; every measurement from `anagraphics`, including
`mongo.operation`, which nothing anywhere could send; `turns.granted` with `fake_purchase`, the only
place turns enter a credit; `preanalysis.turn` with `failed`, a turn the client asked for and did
not get.

**One dimension was loosened.** `preanalysis.turn`'s `model` is optional now. It was required for a
reason that applies to the provider and not to the model — tokens are checked against the provider
— and a turn that failed because nothing came back has no model to name: a call may be refused
before one is chosen, and putting the configured one there would be a claim that it was asked.

## 7. Retention

The daily buckets are small enough that keeping them for ever costs a few megabytes a year, so the
retention exists to be a **decision**, not a rescue. It is a configured number of days
(`limits.retention_days`), applied by a Mongo TTL index like the one already on sessions; `0` means
keep for ever and creates no index. The seed says **90 days**, which is what a new environment is
born with; what runs is what is in Mongo, and it is set to `0` here, because comparing one month
against another is the whole point of collecting these figures.

## 8. How a subsystem measures, and what happens when metrics is down

A shared client in `webtools/commons/metrics/` sends the measurement and **does not wait for it**:
a metrics that is down, slow or full must never make a client's turn fail. What cannot be sent is
lost, and §2 is what makes that acceptable.

A failed send is **not** written to the subsystem's log by default. If metrics breaks while every
subsystem is logging every failure, the logs fill the disk, which is a worse failure than the one
being reported. The capability exists and is configured per subsystem
(`metrics.log_failures`, seeded `false`), to be turned on when somebody is actually looking.

## 9. The API

Write, from the subsystems:

- `POST /measurements` — one measurement: `{subsystem, metric, dims?, count?, duration_ms?, tokens?,
  model?, provider?, project_id?, phase?}`. It is folded into the day's document and, when there is
  a `project_id`, into the project's accumulator. One measurement per request: at the volumes in
  question a batch buys nothing and costs a buffer in memory, a partial-failure answer to define,
  and fifty lost measurements instead of one at a restart. If a volume ever asks for it, it will be
  a second route, `POST /measurements/batch`, leaving this one alone.

Read:

- `GET /metrics/funnel?from=&to=` — the entries and the exits at each gate, **reconciled with
  anagraphics**: beside the counted figure, the one read from the projects, and the difference, so
  an answer says how much of itself was lost. The worst case assumes a 20% conversion; this says
  what it is.
- `GET /metrics/cost?from=&to=` — tokens by phase, by model and by kind; the consumption per
  project as a distribution, not only a mean, and one distribution per kind.
- `GET /metrics/preanalysis?from=&to=` — turns per pre-analysis, how many end `ready` and how many run out.
  `04.` assumes 80–150 turns: this is the answer to that.
- `GET /metrics/providers?from=&to=` — calls, failures, duration at the median and the 95th, from
  the buckets.
- `GET /metrics/http?from=&to=` — requests, statuses and durations by subsystem and route.
- `GET /metrics/economics?from=&to=` — the turns granted against the turns spent, the tokens
  charged to drivers, and the two figures the worst case is built on — **the tokens per accepted
  demo** and **the tokens of what we refused**, by reason.
- `GET /metrics/timing?from=&to=` — how long a project sits at each gate and end to end, at the
  median and the 95th. The driver's hours are counted on every project in the funnel, so a gate
  that takes a week is a cost even when the project never sells.
- `GET /metrics/health?from=&to=` — the system's own state of repair: restarts and starts refused
  for want of a configuration field, calls between subsystems with their failures and latency,
  Mongo's own, and the failure rates of the providers. It is the answer to "is something wrong",
  which today is answered by opening five log files.
- `GET /metrics/projects/{project_id}` — that project's accumulator, next to what anagraphics says
  it consumed.

## 10. The rules it lives by

- **Never in the critical path.** Nothing a subsystem does waits for metrics.
- **It writes nowhere else.** It reads anagraphics to reconcile and to build the commercial funnel;
  it changes nothing there.
- **Its configuration comes from the configurator** (`GET /configuration/metrics`): no defaults, no
  constants in the code, it does not start if a field is missing. Only the bootstrap comes from the
  environment.
- **Who may write is an IP allowlist**, as in anagraphics: an internal service, not on the internet.
- **Tokens are counted, never converted.** No price table, no figure in a currency, and no kind
  added to another.
- **Errors**: the right status and a stable code, `{"error": "<CODE>"}`.
- **No PII and no client text.** Identifiers and numbers. A measurement never carries a message, a
  pre-specification or an answer.

## 11. Open questions

- **The dimensions are a closed list too, or free?** Closed, for the same reason as the names: an
  invented dimension splits a counter in two and nobody notices. But it means a new dimension is a
  configuration change, and that has to be easy.
- **Who looks at it.** For now JSON, read with `curl` or by the configurator's front end. A page of
  its own is a separate decision.
- **The `http.request` metric on the front-gate** counts the showcase site's traffic, which is close
  to web analytics. It stays technical — route, status, duration — and carries no visitor, no
  address, no referrer. If we ever want audience figures, that is a different tool and a different
  decision.
